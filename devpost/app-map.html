Chalkroom App Map

A take-home guide to where things live. Snapshot of commit 9887f99 (2026-10-22). The code can drift after this, so confirm paths with a search.

What it is

You paste study notes. An AI student (Mira, Pip or Juno) picks up believable misconceptions from them. You teach until each belief clears. A judge model decides whether your explanation actually addressed the belief, and what you taught is written on the chalkboard.

:shared

Request/response DTOs, enums and limits that the app and server both compile against (shared/src/main/kotlin/app/chalkroom/shared/Dtos.kt).

:server (Ktor)

The only holder of the Gemini key and every prompt. POST /decks generates misconceptions; POST /lessons/turn judges one explanation.

:app (Compose)

One MVI screen per feature: classroom, choose, paste, reading, lesson, closing. Lesson state is kept locally in LessonRepository.

Evals

JUnit 5 in :server, opt-in with -Pevals. They call Gemini and grade the judge, the say-rules, chalk lines and flaw shaping.

One action, end to end: “Send an explanation”

Reference route: the chalk-line limits

This is the route traced in the Code Tour. It follows how a rule became reliable: a prompt alone (“never more than 8 words”) still produced 9–10-word lines in 1–2 of 15. The fix spread the rule across three layers.

  1. 1Ask for a target in the prompt and require the field in the schema.
    server/src/main/kotlin/app/chalkroom/server/ai/TurnJudge.kt, search Writing "chalkLine" and SCHEMA. The prompt asks for about 6 words (4–8) from your own words. The schema makes addressed, reply and chalkLine required, in that order.
  2. 2Enforce a looser hard limit on the server.
    server/src/main/kotlin/app/chalkroom/server/ai/ChalkLine.kt, MAX_WORDS = 10 in clean(); called from Routes.kt (search ChalkLine.clean) only when addressed. A slightly long line still reaches the board. Only a line long enough to break the layout is dropped.
  3. 3Measure the strict target in the eval.
    server/src/test/kotlin/app/chalkroom/server/evals/SayRulesEval.kt, CHALK_WORDS = 4..8 and chalkLines(), plus Grader.gradeChalkLine. The eval is where prompt drift shows up before a user sees it. The last recorded run: 14/15.

A practice to reuse

Split one AI rule into a target, a hard limit and a measurement. In Chalkroom, the prompt asks for about 6 words. The server accepts up to 10, because a dropped line leaves the board empty, which is worse than a long one. The eval checks 4–8, because a strict eval catches prompt drift early.

On another project with model output inside a product, write the rule down three times: what the prompt asks for, what the code accepts without breaking the UI, and what the eval scores. Keep the eval strictest, keep the runtime forgiving, and log whatever the runtime throws away so that you can see the rate.
